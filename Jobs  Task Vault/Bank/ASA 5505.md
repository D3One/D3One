
# 🔥 Cisco ASA 5505: Segmentation, DMZ, Multi-ISP Failover, and Active Defense

*Author: Ivan Piskunov. All configs below are era-correct (ASA 8.4/9.1 vintage), annotated line-by-line. 

This is a **sample** baseline for a bank with three LAN segments (Servers/DMZ, Users, isolated Bank-Client PCs), three ISPs with tracked failover, and active attack detection/blocking.*

> **Heads-up on licensing & platform realities (ASA 5505):**
> • **Base** license: 3 active VLANs, with the *third VLAN DMZ-restricted* (can initiate to only one other VLAN).
> • **Security Plus**: up to **20 active VLANs**, dual/multi-ISP, VLAN trunks, etc.
> • The 5505 uses **switchports + VLAN SVIs** (no L3 sub-interfaces). Plan per-port VLAN access, not dot1q on the ASA. ([Cisco][1])

---

## 🗺️ High-level design we’ll implement

* **VLAN 10 – INSIDE-USERS** (security-level 100)
* **VLAN 20 – DMZ-SERVERS** (security-level 50)
* **VLAN 30 – BANKCLIENT** (isolated, security-level 60)
* **VLAN 2 / 3 / 4 – OUTSIDE-ISP1/ISP2/ISP3** (all security-level 0)
* **Route tracking (IP SLA)** for **primary → secondary → tertiary** ISPs. ([Cisco][2])
* **Threat-Detection** with **auto-shun** on scanning, plus **SYN flood** controls via **embryonic-connection limits** (MPF). ([Cisco][3])
* Optionally, **IPS** on 5505 via the **AIP-SSC-5** module (if present) inline with fail-open/close policy. ([Cisco][4])

## 🧩 Scenario A — ASA 5505 as the **edge** firewall with 3 ISPs (tracked failover)

> *Assumes Security Plus license.* Replace all IPs with your own. Comments start with `!`.

```cisco
! ========= BASIC ID & MGMT =========
hostname BANK-ASA
domain-name bank.local
crypto key generate rsa modulus 2048         ! SSH needs RSA keys
ssh version 2
aaa authentication ssh console LOCAL         ! 8.4+ requires AAA for SSH
aaa authentication enable console LOCAL
username netops  password <STRONG> privilege 15
username helpdesk password <STRONG> privilege 5
! Lock down who can SSH in (ops subnet only)
ssh 10.10.0.0 255.255.0.0 inside
no telnet 0.0.0.0 0.0.0.0 inside
! Syslog + NTP (SIEM & time-correlation)
logging enable
logging timestamp
logging trap warnings
logging host inside 10.10.60.50
ntp server 10.10.10.10 source inside
```

*Why:* SSHv2 only, per-user accounts with least privilege, and central logging/time are table stakes. Starting in **8.4**, SSH requires AAA/LOCAL users. ([Cisco][5])

```cisco
! ========= VLAN SVIs (L3) =========
interface Vlan10
 nameif inside-users
 security-level 100
 ip address 10.10.10.1 255.255.255.0

interface Vlan20
 nameif dmz-servers
 security-level 50
 ip address 10.20.20.1 255.255.255.0

interface Vlan30
 nameif bankclient
 security-level 60
 ip address 10.30.30.1 255.255.255.0

interface Vlan2
 nameif outside-isp1
 security-level 0
 ip address 203.0.113.10 255.255.255.248

interface Vlan3
 nameif outside-isp2
 security-level 0
 ip address 198.51.100.10 255.255.255.248

interface Vlan4
 nameif outside-isp3
 security-level 0
 ip address 192.0.2.10 255.255.255.248
```

*Why:* security-levels (0..100) gate default flows (high→low allowed, low→high denied unless ACL). Use 50–60 on non-inside networks. ([Cisco][6])

```cisco
! ========= SWITCHPORT → VLAN MAPPING (per-port access; 5505 has an L2 switch) =========
interface Ethernet0/0
 switchport access vlan 2      ! ISP1 modem
interface Ethernet0/1
 switchport access vlan 3      ! ISP2 modem
interface Ethernet0/2
 switchport access vlan 4      ! ISP3 modem
interface Ethernet0/3
 switchport access vlan 20     ! DMZ server switch
interface Ethernet0/4
 switchport access vlan 30     ! Bank-client isolated PCs
interface Ethernet0/5
 switchport access vlan 10     ! Users
interface Ethernet0/6
 switchport access vlan 10     ! Users
interface Ethernet0/7
 switchport access vlan 10     ! Users
```

*Why:* 5505 does **not** do routed sub-interfaces; you assign physical switchports to VLANs. ([PeteNetLive][7])

```cisco
! ========= NAT (object NAT per egress) =========
object network NET_INSIDE
 subnet 10.10.10.0 255.255.255.0
 nat (inside-users,outside-isp1) dynamic interface
 nat (inside-users,outside-isp2) dynamic interface
 nat (inside-users,outside-isp3) dynamic interface

object network NET_DMZ
 subnet 10.20.20.0 255.255.255.0
 nat (dmz-servers,outside-isp1) dynamic interface
 nat (dmz-servers,outside-isp2) dynamic interface
 nat (dmz-servers,outside-isp3) dynamic interface

object network NET_BANKCLIENT
 subnet 10.30.30.0 255.255.255.0
 nat (bankclient,outside-isp1) dynamic interface
 nat (bankclient,outside-isp2) dynamic interface
 nat (bankclient,outside-isp3) dynamic interface

! Static NAT example for a public DMZ service on ISP1:
object network WEB01
 host 10.20.20.10
 nat (dmz-servers,outside-isp1) static 203.0.113.20
```

*Why:* Post-8.3 object NAT per egress interface; routing decides which NAT applies.

```cisco
! ========= ACCESS-CONTROL (examples; tighten to your policy) =========
access-list OUTSIDE_IN extended permit tcp any host 203.0.113.20 eq 443    ! Public HTTPS to DMZ web01
access-list OUTSIDE_IN extended deny ip any any log warnings               ! Default deny with logging
access-group OUTSIDE_IN in interface outside-isp1
access-group OUTSIDE_IN in interface outside-isp2
access-group OUTSIDE_IN in interface outside-isp3

! Inter-VLAN: users to DMZ (app ports), bankclient locked down (only banking backend)
access-list FROM_USERS extended permit tcp 10.10.10.0 255.255.255.0 10.20.20.0 255.255.255.0 eq 443
access-group FROM_USERS in interface inside-users

access-list FROM_BANKCLIENT extended permit tcp 10.30.30.0 255.255.255.0 host 10.20.20.50 eq 443
access-list FROM_BANKCLIENT extended deny ip any any log warnings
access-group FROM_BANKCLIENT in interface bankclient
```

*Why:* Explicit controls beat security-level defaults, especially for audit.

```cisco
! ========= MULTI-ISP FAILOVER (IP SLA / track) =========
! Probe a reliable target per ISP, sourced from that ISP’s SVI
sla monitor 1
 type echo protocol ipIcmpEcho 8.8.8.8 interface outside-isp1
 num-packets 3
 timeout 1000
 frequency 10
sla monitor schedule 1 life forever start-time now
track 1 rtr 1 reachability

sla monitor 2
 type echo protocol ipIcmpEcho 1.1.1.1 interface outside-isp2
 frequency 10
sla monitor schedule 2 life forever start-time now
track 2 rtr 2 reachability

sla monitor 3
 type echo protocol ipIcmpEcho 9.9.9.9 interface outside-isp3
 frequency 10
sla monitor schedule 3 life forever start-time now
track 3 rtr 3 reachability

! Default routes with decreasing priority and tracking
route outside-isp1 0.0.0.0 0.0.0.0 203.0.113.9 1 track 1
route outside-isp2 0.0.0.0 0.0.0.0 198.51.100.9 5 track 2
route outside-isp3 0.0.0.0 0.0.0.0 192.0.2.9   10 track 3
```

*Why:* **Static route tracking** installs backup defaults when probes fail. Syntax varies by ASA code (`sla` vs `sla monitor`), but the method is standard. ([Cisco][2])

```cisco
! ========= ACTIVE DEFENSE: Threat-Detection + auto-shun =========
threat-detection basic-threat
threat-detection statistics host
threat-detection statistics port
threat-detection scanning-threat shun
! Optional sensitivity tuning (use with care; defaults are sane)
! threat-detection rate scanning-threat average-rate 100 burst-rate 300
```

*Why:* **Basic** + **scanning** Threat-Detection surfaces noisy hosts; with **shun**, ASA will **temporarily block** offenders and syslog it (733101/733102). Feed those to SIEM. ([Cisco][3])

```cisco
! ========= SYN flood / brute-force dampening (MPF) =========
class-map CM-DMZ-WEB
 match access-list ACL-DMZ-WEB
!
access-list ACL-DMZ-WEB extended permit tcp any host 10.20.20.10 eq 443
!
policy-map PM-DMZ-PROTECT
 class CM-DMZ-WEB
  set connection embryonic-conn-max 1000 per-client-embryonic-max 30
  set connection conn-max 20000 per-client-max 500
!
policy-map global_policy
 class inspection_default
  inspect dns preset_dns_map
 class CM-DMZ-WEB
  set connection timeout embryonic 0:00:30
!
service-policy PM-DMZ-PROTECT global
```

*Why:* **Embryonic limits** + timeouts slow **SYN floods** and rapid brute attacks against DMZ servers. This is the ASA’s TCP intercept behavior via MPF. Tune to your load profile. ([Cisco][8])

```cisco
! ========= (Optional) IPS module AIP-SSC inline =========
! If your 5505 has the AIP-SSC-5, wire it inline and set fail-open/close:
policy-map global_policy
 class inspection_default
  ips inline fail-open
! Manage signatures/policy via ASDM/IPS Manager Express; keep sigs current.
```

*Why:* The **AIP-SSC** adds signature-based IPS on the 5505 platform (with some feature limits). If you don’t have the module, rely on Threat-Detection + MPF + upstream scrubbing. ([Cisco][4])

## 🧩 Scenario B — ASA 5505 as **internal segmentation firewall**, Kerio UTM at the internet edge

If your Kerio box handles BGP/ISPs at the edge, keep the ASA **inside** to cleanly segment **Users / Bank-Client / DMZ** and to enforce **L3/L4 policy** and **attack dampening** between in-house zones. Re-use all VLAN, ACL, Threat-Detection and MPF bits above; replace the three `outside-isp*` SVIs with one **upstream** VLAN toward Kerio (e.g., `outside-edge`), and route/NAT accordingly.

## 🧪 What happens during an attack (examples)

* **Mass port scans / masscan** → Threat-Detection raises 733101, **auto-shuns** the talker for a period; SIEM alerts; upstream ACLs can add longer shuns. ([Cisco][3])
* **SYN flood** to your DMZ web → MPF embryonic limits throttle half-opens; ASA SYN-cookies kick in; logs show surge; upstream provider can add scrubber if volumetric. ([Cisco][8])
* **Brute-force pop-ups** on known ports → per-client connection caps and short timeouts raise the attacker’s cost; combine with auth rate-limits at the app.

## 🚨 Top 10 network attack themes (2012–2015) you would have seen in a bank

1. **UDP amplification DDoS** (NTP `monlist`, DNS, SSDP, CHARGEN): huge reflection/amplification using spoofed UDP. *Mitigate with upstream ACL/scrubbing, RTBH, provider filtering.* ([CISA][9])
2. **SYN floods**: exhaust connection tables; MPF embryonic limits help. ([Cisco][8])
3. **Volumetric botnet DDoS growth** (pre-Mirai surge): quarterly records noted by Akamai; prep with provider SLAs. ([Akamai][10])
4. **Slow HTTP/S attacks** (e.g., slowloris): tie up web threads; WAF/timeout tuning needed.
5. **SSH/FTP brute-force storms**: use IP reputation, per-client caps, move management off public IPs.
6. **Mass scanning/sweeps**: Threat-Detection scanning + auto-shun + SIEM correlation. ([Cisco][11])
7. **Heartbleed (2014)** on public TLS endpoints: credential/key leakage; immediate patch and cert rotation. ([CISA][12])
8. **Shellshock (2014)** on CGI/Bash paths: remote code exec on exposed web backends. ([success.trendmicro.com][13])
9. **NTP/DNS misconfig exposure** internally: pivot/DoS risks; lock services to mgmt nets only. ([CISA][9])
10. **Basic L3/L4 missegmentation**: flat networks enabling lateral movement; VLANs + ACLs + logging are your friend.
